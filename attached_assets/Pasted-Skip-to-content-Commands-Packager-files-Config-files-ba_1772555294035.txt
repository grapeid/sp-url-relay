Custom Domain Setup Guide
This document explains how to point your own domain at the tunneling hub server so that traffic to your domain (e.g., hub.example.com/alice/) is routed through the server to the appropriate tunnel.

This guide uses Namecheap as the domain registrar, but the DNS concepts apply to any provider.

Prerequisites
The tunneling hub must be deployed (published) on Replit so it has a stable production URL (e.g., your-project.replit.app).
You must own a domain registered with Namecheap (or another registrar).
Step 1: Deploy the Server on Replit
If you haven't already:

Open your Replit project.
Click the Deploy button (or go to the Deployments tab).
The deployment is pre-configured as a VM (always-on) deployment.
Click Publish and wait for the deployment to complete.
Note your production URL — it will look like your-project.replit.app.
Step 2: Decide on Your Domain Structure
You have two main options:

Option A: Subdomain (Recommended)
Use a subdomain like hub.example.com or tunnel.example.com. This is the simplest and most reliable approach because CNAME records work perfectly with subdomains.

Result: https://hub.example.com/alice/page

Option B: Root Domain
Use the root domain directly, like example.com. This is more complex because most DNS providers (including Namecheap) don't support CNAME records on root/apex domains. You would need to use URL forwarding or a provider that supports ALIAS/ANAME records.

Result: https://example.com/alice/page

We recommend Option A for simplicity.

Step 3: Configure DNS on Namecheap
For a Subdomain (Option A)
Log in to namecheap.com.
Go to Domain List in the left sidebar.
Find your domain and click Manage.
Click the Advanced DNS tab.
Click Add New Record and configure:
Field	Value
Type	CNAME Record
Host	hub (or whatever subdomain you want)
Value	your-project.replit.app
TTL	Automatic
Click the checkmark to save.
This tells DNS: "When someone visits hub.example.com, send them to your-project.replit.app."

For the Root Domain (Option B)
Root domains can't use CNAME records. Instead, use Namecheap's URL redirect feature to forward the root domain to your subdomain:

Follow the subdomain steps above first (set up hub.example.com).
In the Advanced DNS tab, click Add New Record:
Field	Value
Type	URL Redirect Record
Host	@
Value	https://hub.example.com
Redirect Type	Permanent (301)
This sends anyone visiting example.com to hub.example.com, which then resolves to your Replit server.

Step 4: Link the Domain in Replit
After DNS is configured, you need to tell Replit about your custom domain:

Open your Replit project.
Go to the Deployments tab.
Find your active deployment.
Look for Custom Domains (or a link/button to manage domains).
Click Add Domain and enter your domain (e.g., hub.example.com).
Replit will verify DNS ownership and automatically provision a TLS/SSL certificate.
This step is required. Without it, Replit won't know to route traffic from your domain to your project.

Step 5: Wait for DNS Propagation
DNS changes can take anywhere from a few minutes to 48 hours to propagate globally, though most changes take effect within 5–30 minutes.

You can check propagation status using:

whatsmydns.net — Enter your domain and select CNAME to see if it resolves correctly worldwide.
Step 6: Verify Everything Works
Once DNS has propagated:

# Check the server is responding on your domain
curl https://hub.example.com
# Expected: "Tunneling Hub is running..."
# Check name availability
curl https://hub.example.com/check-name?name=alice
# Claim a name
curl -X POST https://hub.example.com/claim-name \
  -H "Content-Type: application/json" \
  -d '{"name": "alice"}'
# View active routes
curl https://hub.example.com/status
How Traffic Flows with a Custom Domain
User visits: https://hub.example.com/alice/api/data
        │
        ▼
DNS resolves hub.example.com → your-project.replit.app (CNAME)
        │
        ▼
Replit receives the request, terminates TLS
        │
        ▼
Go API on port 5000 receives: /alice/api/data
        │
        ▼
Go API matches /alice/* → reverse proxy to localhost:10042
        │
        ▼
Chisel tunnel on port 10042 forwards to the connected device
        │
        ▼
Device receives: /api/data (prefix stripped)
Multiple Domains
You can point multiple domains at the same server. For example:

hub.example.com → your-project.replit.app
tunnel.mycompany.com → your-project.replit.app
Both will work because the server accepts traffic from any domain. Just repeat Steps 3 and 4 for each additional domain.

Troubleshooting
"Site can't be reached" or DNS errors
DNS may not have propagated yet. Wait 15–30 minutes and try again.
Verify the CNAME record is correct on whatsmydns.net.
Make sure you added the domain in Replit's Deployments tab.
"Certificate error" or TLS warnings
Replit provisions TLS certificates automatically, but it can take a few minutes after adding the custom domain.
Ensure the domain in Replit's custom domain settings exactly matches your DNS configuration.
API responds but tunnel doesn't work
Verify the Chisel client is connected and the tunnel is active.
Confirm the port in the Chisel client command matches the port returned by /claim-name.
Check that the local service on the device is actually running on the expected port.
Namecheap DNS settings not saving
Make sure you're not using Namecheap's BasicDNS or ParkingPage if you've switched to custom nameservers.
Verify that you're editing DNS under the correct domain.

Tunneling Hub Server Guide
This document provides a complete explanation of how the tunneling hub works, how to interact with it, and how to connect a mobile device or any service through it.

Overview
The tunneling hub is a server that allows remote devices (mobile phones, IoT devices, local development machines, etc.) to expose their local services to the public internet through secure WebSocket tunnels. It works by combining two components:

Go API (port 5000) — The public-facing server that handles name registration, port allocation, AID-based ownership, and reverse proxying of all tunnel traffic.
Chisel (port 8080) — A tunnel server that accepts persistent WebSocket connections from remote devices, creating secure tunnels between the server and each device.
When a device registers a name (e.g., "alice"), it receives a port number. The device then opens a Chisel reverse tunnel to that port. Any public traffic hitting /alice/* on the server is forwarded through the tunnel to the device.

AID-Based Ownership
Names can optionally be associated with an AID (Autonomic Identifier) on first claim. This enables:

Reconnection after restarts: If an agent crashes or restarts, it can reconnect to its previously-claimed name using the /reconnect endpoint with its AID.
Ownership verification: Only the AID that originally claimed a name can reconnect to it or release it.
Graceful shutdown: Agents can voluntarily release their name via /release-name so it becomes available for others.
The current model is trust-on-first-use (TOFU): the AID is associated with the name on first claim. A future enhancement will add KERI signature headers for cryptographic proof of ownership.

Names claimed without an AID work as before but cannot use the reconnect or release features.

API Reference
All API endpoints are accessible through the server's public URL (e.g., https://your-server.replit.app).

Check Name Availability
Checks whether a given name is already claimed.

Request:

GET /check-name?name=alice
Response (available):

{
  "available": true
}
Response (taken):

{
  "available": false
}
Error responses:

400 — Missing or invalid name parameter
429 — Rate limit exceeded
Name rules:

Must be 1–63 characters
Must start with a letter or number
May contain letters, numbers, hyphens (-), and underscores (_)
Case-insensitive (automatically lowercased)
Claim a Name
First-time registration of a new tunnel name. Optionally associates an AID for ownership.

Request:

POST /claim-name
Content-Type: application/json
{
  "name": "alice",
  "aid": "ED4zKjGVbjhKp-otddHszlj0bNERyTKYDS3nTqS7J_av"
}
The aid field is optional. If omitted, the name is claimed without ownership (legacy behavior).

Response (success, 200):

{
  "name": "alice",
  "port": 10042,
  "tunnel_path": "/tunnel",
  "message": "Name claimed successfully"
}
Response (already taken, 409):

{
  "error": "name is already taken"
}
Error responses:

400 — Invalid JSON body or invalid name
405 — Wrong HTTP method (must be POST)
409 — Name already claimed (use /reconnect if you own it)
429 — Rate limit exceeded
500 — Internal error
Reconnect to a Name
Re-establish a previously claimed tunnel connection after agent restart. Requires the AID that was used to originally claim the name.

Request:

POST /reconnect
Content-Type: application/json
{
  "name": "alice",
  "aid": "ED4zKjGVbjhKp-otddHszlj0bNERyTKYDS3nTqS7J_av"
}
Response (success, 200):

{
  "name": "alice",
  "port": 10042,
  "tunnel_path": "/tunnel",
  "message": "Reconnected successfully"
}
The response format is identical to /claim-name so agents can handle both with the same code. The port may differ from the original allocation.

Response (name not found, 404):

{
  "error": "name not found"
}
Response (no owner, 403):

{
  "error": "name was claimed without an AID and cannot be reconnected"
}
Response (AID mismatch, 403):

{
  "error": "aid mismatch: name is owned by a different identity"
}
Error responses:

400 — Invalid JSON body, invalid name, or missing AID
403 — Name has no AID owner, or AID does not match the stored owner
404 — Name not found in the database
405 — Wrong HTTP method (must be POST)
429 — Rate limit exceeded
500 — Internal error
Release a Name
Voluntarily release a claimed name during graceful shutdown. Frees the port immediately and makes the name available for anyone to claim again.

Request:

POST /release-name
Content-Type: application/json
{
  "name": "alice",
  "aid": "ED4zKjGVbjhKp-otddHszlj0bNERyTKYDS3nTqS7J_av"
}
Response (success, 200):

{
  "message": "Name released successfully"
}
Response (name not found, 404):

{
  "error": "name not found"
}
Response (no owner, 403):

{
  "error": "name was claimed without an AID and cannot be released"
}
Response (AID mismatch, 403):

{
  "error": "aid mismatch: name is owned by a different identity"
}
Error responses:

400 — Invalid JSON body, invalid name, or missing AID
403 — Name has no AID owner, or AID does not match the stored owner
404 — Name not found in the database
405 — Wrong HTTP method (must be POST)
429 — Rate limit exceeded
500 — Internal error
View Status
Lists all currently claimed names and their allocated ports.

Request:

GET /status
Response:

{
  "active_routes": {
    "alice": 10042,
    "bob": 10043
  },
  "count": 2
}
Agent-Side Flow
The recommended flow for an Identity Agent on startup:

1. Load saved tunnel settings (provider, domain, extension/name)
2. Load agent AID from identity store
3. Try POST /reconnect {"name": "<extension>", "aid": "<AID>"}
   -> 200? Parse response, connect Chisel tunnel. Done.
   -> 404 (name not found)? Go to step 4.
   -> 403 (AID mismatch)? Fail with error - someone else owns this name.
   -> Connection error / other? Go to step 4.
4. Try POST /claim-name {"name": "<extension>", "aid": "<AID>"}
   -> 200? Parse response, connect Chisel tunnel. Done.
   -> 409 (already taken)? Fail with error.
   -> Other error? Fail with error.
On graceful shutdown:

1. POST /release-name {"name": "<extension>", "aid": "<AID>"}
   -> Best-effort, 3-second timeout. Log result but don't block shutdown.
2. Close Chisel client.
Connecting a Device via Chisel
After claiming a name and receiving a port number, the remote device must establish a Chisel reverse tunnel.

Step 1: Install Chisel on the Device
Download the appropriate Chisel binary for your device from github.com/jpillora/chisel/releases.

Step 2: Connect the Tunnel
Run the Chisel client on the device, pointing it at the server's /tunnel path:

chisel client --auth user:secret-token https://your-server.replit.app/tunnel R:<allocated-port>:<local-address>
Example: If you claimed the name "alice" and received port 10042, and your local service runs on port 3000:

chisel client --auth user:secret-token https://your-server.replit.app/tunnel R:10042:localhost:3000
This tells Chisel:

Connect to the server via the /tunnel path (WebSocket upgrade handled by the Go API)
Authenticate with user:secret-token
Reverse-forward port 10042 on the server to localhost:3000 on the device
Important: The Chisel server is accessible only through the /tunnel path on port 443 (HTTPS). It is not available on a separate port (e.g., 8080) from outside the server. The Go API reverse-proxies WebSocket connections from /tunnel to the internal Chisel server.

Step 3: Verify
Once the tunnel is established, public traffic to https://your-server.replit.app/alice/ will be forwarded to localhost:3000 on the device.

For example:

https://your-server.replit.app/alice/api/data -> device receives request at /api/data
https://your-server.replit.app/alice/page -> device receives request at /page
Note: The /alice prefix is stripped before forwarding. The device sees clean paths without the name prefix.

Full Workflow Example
Here is a complete example of a mobile app connecting through the hub with AID-based ownership:

# 1. Check if the name "myphone" is available
curl https://your-server.replit.app/check-name?name=myphone
# Response: {"available": true}
# 2. Claim the name with an AID
curl -X POST https://your-server.replit.app/claim-name \
  -H "Content-Type: application/json" \
  -d '{"name": "myphone", "aid": "ED4zKjGVbjhKp-otddHszlj0bNERyTKYDS3nTqS7J_av"}'
# Response: {"name": "myphone", "port": 10044, "tunnel_path": "/tunnel", "message": "Name claimed successfully"}
# 3. On the mobile device, start a local web server on port 8000
# (this depends on your app - could be Flask, Express, etc.)
# 4. Connect chisel tunnel
chisel client --auth user:secret-token https://your-server.replit.app/tunnel R:10044:localhost:8000
# 5. Now anyone can access the device at:
#    https://your-server.replit.app/myphone/
# 6. After a restart, reconnect using the same AID
curl -X POST https://your-server.replit.app/reconnect \
  -H "Content-Type: application/json" \
  -d '{"name": "myphone", "aid": "ED4zKjGVbjhKp-otddHszlj0bNERyTKYDS3nTqS7J_av"}'
# Response: {"name": "myphone", "port": 10045, "tunnel_path": "/tunnel", "message": "Reconnected successfully"}
# 7. On graceful shutdown, release the name
curl -X POST https://your-server.replit.app/release-name \
  -H "Content-Type: application/json" \
  -d '{"name": "myphone", "aid": "ED4zKjGVbjhKp-otddHszlj0bNERyTKYDS3nTqS7J_av"}'
# Response: {"message": "Name released successfully"}
Rate Limits
The API enforces per-IP rate limiting to prevent abuse:

Endpoint	Burst Limit	Refill Rate
GET /check-name	30 requests	5 per second
POST /claim-name	10 requests	1 per second
POST /reconnect	10 requests	1 per second
POST /release-name	10 requests	1 per second
GET /status	30 requests	5 per second
When the rate limit is exceeded, the server responds with HTTP 429:

{
  "error": "rate limit exceeded, try again shortly"
}
Data Persistence
All claimed names, port allocations, and AID ownership are stored in a PostgreSQL database. If the server restarts, all names and routes are automatically restored from the database.

Database schema:

CREATE TABLE claimed_names (
    id SERIAL PRIMARY KEY,
    name VARCHAR(63) UNIQUE NOT NULL,
    port INTEGER NOT NULL,
    aid TEXT,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

# Tunneling Hub Server Guide

This document provides a complete explanation of how the tunneling hub works, how to interact with it, and how to connect a mobile device or any service through it.

---

## Overview

The tunneling hub is a server that allows remote devices (mobile phones, IoT devices, local development machines, etc.) to expose their local services to the public internet through secure WebSocket tunnels. It works by combining two components:

1. **Go API** (port 5000) — The public-facing server that handles name registration, port allocation, AID-based ownership, and reverse proxying of all tunnel traffic.
2. **Chisel** (port 8080) — A tunnel server that accepts persistent WebSocket connections from remote devices, creating secure tunnels between the server and each device.

When a device registers a name (e.g., "alice"), it receives a port number. The device then opens a Chisel reverse tunnel to that port. Any public traffic hitting `/alice/*` on the server is forwarded through the tunnel to the device.

---

## AID-Based Ownership

Names can optionally be associated with an AID (Autonomic Identifier) on first claim. This enables:

- **Reconnection after restarts:** If an agent crashes or restarts, it can reconnect to its previously-claimed name using the `/reconnect` endpoint with its AID.
- **Ownership verification:** Only the AID that originally claimed a name can reconnect to it or release it.
- **Graceful shutdown:** Agents can voluntarily release their name via `/release-name` so it becomes available for others.

The current model is trust-on-first-use (TOFU): the AID is associated with the name on first claim. A future enhancement will add KERI signature headers for cryptographic proof of ownership.

Names claimed without an AID work as before but cannot use the reconnect or release features.

---

## API Reference

All API endpoints are accessible through the server's public URL (e.g., `https://your-server.replit.app`).
